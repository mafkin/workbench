# Workbench: context for Claude sessions

This is a personal Linux workbench for one user. It's a local web app with a React UI and a Fastify service on `127.0.0.1:7420`. Everything it keeps lives in one folder the user picks at setup (part 13); profiles are its subfolders, each with its own configurable left nav panel. The app is built **part by part**; parts 1 to 10 are done. Start with the decisions and per-part notes in [docs/roadmap.md](docs/roadmap.md). The [README](README.md) covers usage and the config format.

## How to work with this user

- **Ask before you build.** The user wants to design each part themselves ("I want to build this part by part the way I want"; "look at its features and ask what I want"). At the start of a part:
  1. Ask about the decision points listed for it in `docs/roadmap.md`. Use multiple-choice questions with 2-4 options, put the recommended option first, and add previews for visual choices.
  2. Then write the plan.
- **Plan first.** Any change touching more than two files gets a short plan in Plan Mode, approved before you write code. Part 1's plan used these sections: Context, Where things live, Stack, Files, Behaviour, Verification.
- **Bug fixes are test-first.** Write a minimal failing test that reproduces the bug, then fix it, then run the tests until they pass.
- **Secrets.** Never print or ask for tokens or passwords in chat; the user edits `.env` files themselves.
- **Failures.** When something fails, give the exact command and its output.
- **Trying changes.** The user runs the app on their desktop and pulls changes to try them. At the end of a part, say what to pull and what to click.

## Commands

```sh
npm install
npm test           # Vitest: 371 tests (the wiki store and pages, setup, guard, launch, notes, wiki links, files, steps, cards, chats, agent profiles, backgrounds, context, Claude setup, MCP checks and switches, masking, profiles, switcher, servers, git, thumbnails, .blend, open with, drawers, logos, HTTP API)
npm run e2e        # Playwright: 113 tests (two e2e services: the fixture's on 7431 and one without a folder on 7432 for the setup screen); in a fresh environment run `npx playwright install --with-deps chromium` first
npm run build      # tsc -p . (TypeScript 7) + vite build
npm run dev        # service on 7420 (node --watch) + Vite with hot reload on 7421 (proxies /api)
bin/workbench      # desktop only: start the service if needed, then open the window
bin/workbench --install | --uninstall | --print-units | --update   # systemd user units (start at login; rebuild and restart after a pull)
bin/workbench --dir PATH   # set the Workbench folder without the setup screen
```

Run `npm test`, `npm run e2e` and `npm run build` before you call a part done. In a cloud container whose preinstalled Chromium doesn't match Playwright's version, don't download browsers: run e2e with an untracked config that spreads `playwright.config.ts` and sets `use.launchOptions.executablePath: '/opt/pw-browsers/chromium'`. Desktop actions do nothing in a cloud container: `xdg-open`, launchers, "Open in Files", the GNOME launcher. That's expected. The e2e server fakes `spawn` and logs launches to a file, so tests never start real programs; its fake `gio trash` moves files into the fake home's XDG Trash (`e2e/.tmp-config/home/.local/share/Trash`, with `.trashinfo` files; `TRASH` and `TRASH_DIR` in `e2e/fixture.ts`). Chats in tests run `tests/fixtures/fake-claude.mjs` and `fake-shell.mjs` in real PTYs (passed as `chatCommands`), never the real claude. Keep it that way. MCP checks in tests start `tests/fixtures/fake-mcp.mjs`, a stdio MCP server whose behaviour is chosen by `FAKE_MCP_MODE`. HTTP and SSE servers are in-test HTTP servers. The e2e server clears `CLAUDE_CONFIG_DIR` and passes `managedDir` into the fixture, so it never reads the machine's own Claude files. The e2e fixture runs `git init -b main` in `~/alpha`, so `git` must be installed. Unit tests run `tests/setup-env.ts` first (vitest `setupFiles`): it points `WORKBENCH_STATE_DIR`, `XDG_STATE_HOME` and `XDG_CACHE_HOME` at a temp folder and clears `CLAUDE_CONFIG_DIR`, so a test can never touch the running service's state, the thumbnail cache or the machine's Claude files; still pass `stateDir` (and `gitFetchEveryMs: 0`) to every `buildServer`.

## Conventions and gotchas

- **Server TypeScript runs directly on Node 26** (type stripping). Only erasable syntax: no enums, no parameter properties. Imports use `.ts` extensions.
- **Imports:** `moduleResolution: nodenext`, so packages without an `exports` map need full subpaths, e.g. `lucide-react/dynamic.mjs`.
- **Pages are the config (part 11).** The in-memory `Profile`, `ItemAddr` and the `Op` list are unchanged; only `server/wiki.ts` knows about files. Addresses index the lists in the page in file order, so a line the store cannot read still takes its place (as a note opening the page). A `[[Page]]` is found by path, else by name (pages/ first, then projects/, then the root); `linkOf` writes the name when it is unique. Paths with spaces are percent-encoded in links; `run:`/`chat:` lines with spaces go in angle brackets. Frontmatter is edited through a yaml Document (comments kept; spacing before a comment normalizes). A bare `~` is YAML null in frontmatter too, so write `home: "~"`. Tests that need a profile write YAML and call `migrateFixture(cfg, home)` (unit: the Workbench folder is `<home>/wb`, so the work profile is `~/wb/work`) or `writeWork` (e2e: `<HOME>/workbench`, so `~/workbench/work` and `~/workbench/personal`; `WB`, `NOTES`, `PNOTES` in `e2e/fixture.ts`). The YAML's old `notes:`/`home:` keys are ignored. `resetFixture` keeps the Workbench folder and its `settings.yaml` in place and rewrites them, because a watch on a folder deleted and made anew goes quiet. `Profile.root` is in `~/…` form; a profile parsed bare in a test has `root: '~'`, no drawer folder and no browse root of its own.
- **Style:** dark only, tame colours, using the tokens from `theme.css` (never hard-coded colours: themes swap the tokens). With a background, `.nav` and `.main` are translucent; give new surfaces that hold text a solid token background (`--bg`, `--panel`) so they stay readable over a picture. Small uppercase muted headings, a 2px accent bar plus a soft accent background on the selected row. Keep new UI consistent with this.
- **UI state:** per-browser state (nav width, collapsed headings, selection) lives in localStorage, read through `src/lib/local.ts` with try/catch. Anything the user configures belongs in the YAML.
- **Testing drag and drop:** Playwright drags need `mouse.down` followed by moves with `steps`; see `e2e/nav.spec.ts`.
- **File access:** any new route that reads or writes user files goes through a confinement check like `Notes.#resolve` (realpath, then allowed roots). Part 3's file browser should reuse that approach.
- **`fs.watch` on Linux:** a watch on a folder that gets deleted goes quiet without an error; the only sign is an event named after the folder itself (see `Notes.#replaced`).
- **react-markdown components:** a component defined inline is a new type on every render and remounts; keep stateful ones (like images, which fetch) at module level.
- **Images in notes** load through `fetch` + blob URLs, because `<img>` can't send the X-Workbench header. File previews use `/raw/` tickets instead, which also give Range requests for seeking in video.
- **Drawers in addresses:** `ListAddr`/`ItemAddr` have `drawer?` (missing = 0). `itemKey` writes `d:s.i` only past the first drawer, so old keys and the first drawer's addresses look as before; `parseKey` reads both. Code that walks entries uses `walkItems`/`allSections`/`sectionsOf`, never `profile.sections` (empty once `drawers:` exists). NavPanel builds addresses with `inDrawer`, and its `Ctx` carries `drawer` and `sections`. A `shared` entry: `entryAt`/`findShared` give the original; the selection keeps the shared entry's `addr` (nav, drawer) with `item`/`origin` from the original (MainPane passes `origin` to pages).
- **Selection keys:** an entry address, `note:<path>`, `files:<path>`, `context:<name>`, `setup:` or `servers:`. An address is stored with `selectedId` (`entryId`: type, label, path); `resolveEntry` finds the entry again after a move. `openNote`/`openFolder` in App pick the nav entry instead when one has the same path, so the nav highlights it.
- **Items:** `type: folder` and `type: item` are the same kind in code (`folder`); `path` may be missing. Key anything about an item by `projectRef(item)`, never `item.path`, and resolve step paths against `itemBase(profile, item)`. Code that needs a folder uses `itemsWithFolder` or checks `item.path`. Step indexes of an old project depend on whether it is in a repository: the service uses `stepsFor` (ops route, `/api/open`, `/api/chats`), the page uses the git marks, and step ops from the page carry `seed`.
- **Repeated nav: avoid it unless it makes sense.** The user wants the left panel to choose and the centre to hold the workflow, so don't add lists of nav entries or chips of folder entries to Home or the main pane just to navigate. It isn't a strict rule: "if it makes sense it should be implemented" (e.g. the Claude setup page's For picker lists the projects).
- **Context and chat args:** every claude chat in a wiki profile gets `wikiContext` (the wiki root in `--add-dir`, the pages' layout in the prompt), so exact-args assertions in chat and agent specs start with `--append-system-prompt` and `--add-dir <wiki>`; the e2e fixture has no `~/notes/context`, so only `context.spec.ts` sees the context folders too. `agentArgs(profile, home, cwd, context)` must keep one `--append-system-prompt` and one `--add-dir`, with list flags last; `agentFor` merges context, wiki and drawer folders into that one pair.
- **Skills reach claude two ways (part 12):** installed skills are only named in the prompt (claude loads them anyway; there is no per-session allowlist); the wiki's `skills/` are loaded through `--plugin-dir` (before the list flags) and show as `/wiki:<name>`. Never copy skills into `~/.claude` or a project's `.claude`. A chat's bundle must stay where its saved args point (`<state>/skills/<hash>/wiki`); `prune` keeps those.
- **The session hook in args:** every claude chat's args end with `--settings <json>` after the session flag (`#hookArgs`), so exact-args assertions end with `"--settings"`; the fake claude reads it and runs the hook on start and on a `clear` command. Tests that measure output skip the `args=` line.
- **Git in tests:** use real git in temp folders with a bare remote and a second clone as "someone else"; the service runs git with `HOME` = its `home`, so write `~/.gitconfig` (identity, `init.defaultBranch`) in the fake home, and run the test's own git with the same HOME and `GIT_*` variables removed. e2e: the fixture's `~/alpha` is a repo, so Alpha has a git mark in the nav in every spec; `git.spec.ts` and `setup.spec.ts` write `WORK_DRAWER` (the work profile as one drawer with `folder: ~/alpha`) so the rail's Git and setup views act on it, and only `git.spec.ts` commits and adds a remote. Pass `gitFetchEveryMs: 0` to `buildServer` unless a test is about the background fetch.
- **Servers in tests:** start a real `node -e` HTTP server with `cwd` inside a project and read its port from stdout; kill it in `afterEach`. Never stop anything that isn't the test's own child.
- **Effects return a cleanup function or nothing.** A returned value is called as a cleanup and crashes the page. DOM methods that used to return `undefined` now return a Promise (`scrollIntoView`, `scrollTo` in Chromium 156), so `if (el) return el.scrollIntoView()` breaks. The cloud's older preinstalled Chromium hides this; the desktop's e2e (Playwright's own Chromium) catches it.
- **Process names:** `/proc/<pid>/comm` is the main thread's name, which Node 26.11 sets to `node-MainThread`. `Procfs.process` names a process after its program (`argv[0]`) and uses `comm` only when the command line was rewritten into one string.
- **Bundle size:** the main chunk must stay under 800 kB (about 600 kB now; the schema and zod sit in a 103 kB `config-schema` chunk the main one loads at start, split out since the lazy DrawerDialog shares it). Don't import lucide icons in `ContextMenu.tsx`: it pulls a shared chunk (~110 kB) into the main one; its tick is CSS. New views go in lazy chunks (`ServersView`, `GitView`, `ModelPreview` with three.js, `QuickSwitcher`, `ProfileDialog`, Markdown, the highlighter). Import three only from `ModelPreview.tsx` (and dynamically from `src/lib/thumbs.ts`).
- **Assets in tests:** e2e builds its sample assets in `gallery.spec.ts` (PNGs with `encodePng`, a glTF triangle with a `.bin`, a WAV, a synthetic `.blend`, a Godot project) and uses `openWith:` rules for Blender/Godot, since neither is installed; launches land in the fake spawn's log. The e2e thumbnail cache (`THUMBS`, `e2e/.tmp-thumbs`) must stay outside the config folder, which the service watches. WebGL works in headless Chromium (software rendering). Effects in components must not return a value from a callback (`useEffect(() => fn(x))` returning a number crashes React as a "cleanup").
- **`~/.claude.json` writes:** only through `setFoldersOff`, and only the `disabledMcpServers` list. Claude files a folder under its git root (`projectKey`), so use that key, never the folder as given. A running claude re-reads the file when it changes (checked on the desktop), so outside writes survive.
- **Claude setup secrets:** anything read from claude's files goes through `server/mask.ts` before it is sent; raw configs stay in the service (`SetupRead.servers`). JSON parse errors are reported without the text they quote. A check is by id only and re-reads the files. In e2e, `writeClaudeSetup()` is called only by `setup.spec.ts` and `skills.spec.ts`, so other specs see Alpha without `.mcp.json` or `.claude/`.
- **Step paths** are relative to the project (`stepPath`); folder steps (and the folders of report and file steps) count as browse roots (`folderRoots`), and note steps as note entries, so a step outside its project still works.
- **Chat sockets:** refuse a WebSocket upgrade in the route's `preValidation`, not in `onRequest`: refused there, @fastify/websocket leaves the connection open and `app.close()` hangs. The guard skips `/pty/` upgrades in `onRequest` for that reason.
- **Chat tests:** `Chats.text()` uses `translateToString(true)`, which trims trailing spaces, so wait for `args=` rather than the `> ` prompt. In e2e, read the screen from `.chat-terminal .xterm-rows` (the dock's is `dock.locator(...)` when a step's chat shows in the page too), and `closeChats()` in `beforeEach` (the service outlives tests). The prompt is long enough to scroll the banner away, so the fake claude repeats `FAKE CLAUDE cwd=… resumed=… short=[…]` (long values shortened) after `args=`; assert flags on `short=`, prompt text in unit tests. Typing `size` makes it print its terminal's size (`size=<cols>x<rows>`). The e2e server shortens needs-you timings (`chatTiming`).
- **`agent:` means three things:** on a chat step or entry it is `claude`, `shell` or an agent profile name (`chatProgram` gives the program); on a folder entry it is a card field, the default for New chat. Unknown names are refused when a chat starts (422), not by the schema, so a typo never breaks the whole file.
- **Comments on a key's line:** `applyOps(doc, ops, source)` needs the file text to keep `key: # comment` on its line when the value is a block map or list; the store passes it.
- **Card fields** (`CARD_FIELDS`) are not in `TYPE_FIELDS`, so editing an entry in the dialog keeps them. `status: active` is written by leaving the field out. Pinned-first sorting and hiding archived projects happen only outside nav edit mode, because dnd-kit indexes must match the file.
